The pitch for islands architecture is usually framed as "ship less
JavaScript." That is true but it undersells the thing that actually changes
how you build.

In a typical single-page app, adding an interactive component costs nothing
visible. The runtime is already there. The bundler already runs. One more
component is a rounding error against a bundle you have already decided to
pay for — so nobody argues about it, and the bundle grows for years.

## What changes

In an islands app the default is zero. A page ships no JavaScript until you
write `client:load` — and the moment you do, you are not adding a component,
you are opening an account. The framework runtime, the component, and its
dependencies all arrive for that one island.

That makes the cost *legible*. And legible costs get argued about, which is
the entire point.

## The question it forces

Every time I reach for an island now, the same question comes up: does this
need to be interactive, or does it just need to look interactive?

A surprising amount of the second category has a native answer:

- Disclosure widgets → `<details>`
- Modals → `<dialog>`
- Menus and tooltips → the `popover` attribute
- Reveal on scroll → `animation-timeline: view()`
- Filtering a list → generate the filtered pages at build time

None of those ship a runtime. Most of them are also more accessible than what
I would have written by hand, because the browser has already solved focus
management and keyboard behaviour.

## Where islands earn it

This is not an argument against interactivity. Some things genuinely need
state that lives in the browser: a command palette, a text editor, a canvas,
anything with real-time data.

The point is that islands turn "should this be JavaScript?" from a question
nobody asks into a question you cannot avoid asking. Most of the wins come
from asking it, not from the architecture itself.
