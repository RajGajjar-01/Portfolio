You store the theme in state, read it on mount, apply the class. It works —
except for the white flash on every page load before your JavaScript runs.

The usual response is to reach for a bigger hammer: move it to context, move
it to a provider, persist it to a cookie and read it server-side. Those can
work, but they are solving the wrong problem.

## The actual constraint

The browser paints as soon as it can. Anything that runs after that first
paint is, by definition, too late to prevent a flash. Deferred scripts,
hydration callbacks, effects — all of them run after.

So the fix is not about *where* the state lives. It is about running the code
before the first paint, which means exactly one thing: a synchronous inline
script in `<head>`.

```html
<script is:inline>
	const theme = localStorage.getItem('theme');
	if (theme === 'light' || theme === 'dark') {
		document.documentElement.dataset.theme = theme;
	}
</script>
```

Blocking scripts are usually a mistake. This is the case where blocking is the
entire point — it is a handful of bytes, and it must finish before paint.

## Let CSS own the default

The part people over-build is the system preference. You do not need to read
`matchMedia` in JavaScript and write the result back. If there is no stored
choice, write nothing, and let the stylesheet decide:

```css
:root {
	--bg: white;
}

:root[data-theme='dark'] {
	--bg: black;
}

@media (prefers-color-scheme: dark) {
	:root:not([data-theme='light']) {
		--bg: black;
	}
}
```

Three states, no JavaScript: explicit dark, explicit light, and "follow the
system" as the absence of an attribute. The `:not([data-theme='light'])` guard
is what lets an explicit light choice override a dark system preference.

The script only ever handles the one thing CSS cannot: remembering what the
user clicked.
