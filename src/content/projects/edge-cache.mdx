## The problem

Our product API served the same handful of read endpoints to every user on
every page load. Each request travelled to a single region, hit Postgres, and
came back. For users outside that region, the network round trip dominated:
p95 sat around 340ms, and roughly 80% of that was distance, not compute.

## Approach

The obvious fix — a bigger cache in front of the database — would not have
helped, because the latency was geographic. The cache had to live near the
user.

I built a read-through cache as a Worker that sits in front of the origin API:

- Cache keys derive from the route plus the authenticated tenant, so tenants
  never share entries.
- Writes publish invalidation events; the Worker purges by tag rather than
  waiting for a TTL.
- On a miss the Worker fetches from origin, stores, and serves — so a cold
  edge costs one extra hop, never an error.

## Outcome

| Metric | Before | After |
| --- | --- | --- |
| p95 latency | 340ms | 28ms |
| Origin requests | 100% | 6% |
| Database CPU | 71% | 22% |

The 6% miss rate is mostly first-request-per-region traffic, which is the
floor for this design.

## What I would change

Invalidation is tag-based and fires on every write, which means a hot tenant
can generate more purge traffic than read traffic. Batching purges into a
short window would trade a little staleness for a lot less churn.
